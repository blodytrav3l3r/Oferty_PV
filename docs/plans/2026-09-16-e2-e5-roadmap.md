### E2.0 Baseline (bez kodu)

### P1.1a Threat/model review draftu (BEZ KODU — twardy gate)

Protokół w `docs/plans/e2-draft-review.md`. P1.1b NIE startuje, dopóki WSZYSTKIE

### D2 Permission matrix (dokument + testy, w E2)

Plik: `docs/security/permission-matrix.md` (nowy katalog — jedyny nowy katalog
w tym planie). Kolumny: route, operation, required permission, owner required,

### P1.3 Limity JSON

- Pliki: `src/app.ts:208`, `src/mountRoutes.ts:59`.
- Cel: global w dół (np. 1mb), 50mb tylko offers/orders/import.
- Akceptacja: 413 na małej trasie przy dużym payloadzie; duże importy działają.

### P1.5 Lock-GET fresh

- Pliki: `src/routes/locks.ts:105`, `src/utils/docLocks.ts:46`.
- Cel: wygasły lock → `locked:false` + lazy-delete; acquire wymaga read-access.
- Akceptacja: test lock-squattingu (obcy nie blokuje cudzego docId).

### P1.4 Auth (rozbite na 4 kroki — zmiana większa niż wygląda)

- P1.4a Auth flow audit (BEZ KODU): mapa `login → cookie/session → iframe → SPA →
API → refresh → logout → multi-tab → 401/403`; wykryć miejsca faktycznie
  wymagające tokenu po stronie JS.
- P1.4b Decyzja/protokół (httpOnly-first albo udokumentowane odstępstwo).
- P1.4c Implementacja (`public/js/shared/auth.js`, `src/routes/auth.ts`).
- P1.4d Test regresyjny sesji w SPA/iframe.
- Akceptacja: sesja działa w SPA; brak tokenu w JS-storage (lub krótki TTL + rotacja).

### P1.6 Solver determinizm

- Plik: `public/js/studnie/solverAutoSelect.js`.
- Cel: tolerancje do nazwanych stałych domenowych; test-matryca input → output
  identyczny niezależnie od czasu; memo tylko per-run (zostaje).
- Akceptacja: identyczne wejście (input + config + katalog) → identyczny wynik.

### P1.7 DevOps (walidacja runtime wcześniej, nie osobny megakrok)

- Pliki: `Dockerfile`, `src/app.ts:94/114/130`.
- Cel: `USER node` + chown `/var/data`; HEALTHCHECK na `/health/ready`; PRAGMA sekwencyjnie.
- Walidacja od razu po zmianie: build → start → migrations → health → DB write →
  DB read → permissions → shutdown/restart.
- Akceptacja: kontener healthy tylko przy żywej DB; pełny cykl start/stop bez błędów.

### P1.1b Implementacja draftu wg protokołu P1.1a

- Pliki: `public/js/...` (wg protokołu) + test.
- Cel: crash/refresh → odzysk; draft NIGDY nie nadpisuje SAVED.
- Akceptacja: zamknięcie karty / crash / refresh → pełny odzysk niezapisanych zmian.

### GATE E2 / GATE E2-final + DoD E2

Gate E2 (po P1.7): `npm run validate` PASS + wszystkie testy P1 zielone.
Gate E2-final (po P1.1b): to samo + odzysk draftu.

- E2-D1 Security regression: stare testy security + nowe testy P1 + pokrycie macierzy D2.
- E2-D2 No behavior regression: auth, locki, solver, iframe/SPA, draft/SAVED bez zmian niezamierzonych.
- E2-D3 Migration/backward compat: istniejąca DB → upgrade → start → dane czytelne (jeśli P1 zmienia strukturę/kontrakt).
- E2-D4 Rollback: każdy większy P1 ma udokumentowaną ścieżkę powrotu (nie automat, tylko opis).

## D1 Restore drill (TERAZ na dev, później produkcyjny)

Kolejność: izolowana kopia dev TERAZ (nigdy produkcyjna DB); manual production
drill obowiązkowo przed oznaczeniem backupu jako bojowego. Scenariusze:
fresh-env, corrupted-checksum, corrupted-sqlite, missing-sidecar,
migration-mismatch, wrong-version. Wynik: realne RTO, RPO, czas restore.
Bez PASS drillu backup nie jest bojowy.

## Reguły realizacji

Security > dane > testy > perf > refaktor. Każdy task: problem, dowód
(plik:linia), wpływ, ryzyko, minimalny diff, centralny mechanizm, test
regresyjny, kryterium akceptacji. Przed commitem: `npm run version:check` +
`npm run validate` + `npm run format`. Commity helperem
`node scripts/commit.mjs` (polskie znaki).
